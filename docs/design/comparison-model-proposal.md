# Comparison model proposal

Status: proposed, not started. The benchmark tooling grew around one operation, complete serial sorting, and now also measures argsort, selection and Rayon sorting; 0.2 adds parallel argsort. This page owns the planned identity model, names, plan and data formats, and the per-operation comparison pages until they land. The rules for choosing references and cases are current and belong to the [benchmark protocol](../development/benchmarking.md#choosing-references-and-cases); current module boundaries belong to [benchmark tooling](benchmark-tooling.md). When a stage lands, move its facts to those owners and delete it here.

## Problem

A measurement has four independent dimensions, but the tooling encodes them in overlapping places, each defaulting to serial full sorting:

- **Execution is encoded three times.** Thread counts are part of implementation IDs (`tessera-par-4`, `rayon-stable-8`), of a separate `[[parallel]]` plan rule kind and of catalog `modes` (`par`, `par-1` … `par-8`). Each new thread count or parallel opponent adds catalog IDs, so identities grow as implementations × thread counts. Parallel rules cannot carry an operation, so a plan cannot express `par_argsort`.
- **Operation is encoded twice.** Plans carry `operation`, while `modes` are named after the sort entry point their full sorts call (`sort`, `sort_unstable`, `par_sort`). A plan's `schema` number also discriminates the operation: sorting plans use schema 1, other operations schema 2, and schema 1 include rules may carry their own operation that algorithm comparisons reject.
- **Case IDs are asymmetric.** Full sorts have no operation component (`type/distribution/length/seed`); other operations append one (`…/select/32768`); Criterion IDs add a `rust/` prefix and a trailing mode. Execution has no component, so readers recover it from the implementation ID or from the last path segment.
- **One concept has several names.** The measured result is called operation, mode, workload or task (`types.task` means keys versus records). The input pattern is a distribution on the CLI and in the catalog but a shape in `--group TYPE/SHAPE`, `summaryShapes` and the code. A case selection is a plan on the CLI and a suite in direct executables. Selection is `select` in plans and IDs, `select_nth` in the API and figures, and "Stable selection" in reports.
- **"Algorithm" means the competitor.** `compare algorithms`, the catalog's `algorithms` and the `benchmark-data/<algorithm>/` directories identify who implements a result, while contributors also call argsort or selection "algorithms".
- **Implementation entries carry sort semantics.** `std-stable` is labelled `slice::sort`, although its argsort route sorts an index vector by key and its selection route sorts the whole input. `stable` and `family` describe a route: `std-unstable` selects with `select_nth_unstable`. `tessera-full` is a route (a full sort used as a selection reference) with its own identity.
- **Reports and publication assume sorting.** The report charts fix "speed vs slice::sort" as the denominator, `catalog.comparison` holds only the sort ranking cohort, and tracking runs, `comparison.json` and `growth.json` have no operation or execution field. Retired operations (`top-k`, `segments` and others) share the live operation union because retained results still decode them.

## Model

```text
case        = operation × execution × input
measurement = implementation × case, carried out by a route
```

| Concept | Meaning | Owner |
|---|---|---|
| **Operation** | The caller-visible result, named by the public API: `sort`, `argsort`, `select_nth`, `sort_by_cached_key`. Parameters such as the selected rank belong to it. | A catalog `operations` table: name, parameters, reference implementation, default cohort and section order |
| **Execution** | `serial`, or a worker count `tN` for the `par_` form of the operation. `par_argsort` is operation `argsort` with execution `t4`, not a separate operation. | A case axis; plans select thread counts like lengths |
| **Input** | Record type, distribution, length and seed, generated by `case.rs`. | Unchanged |
| **Implementation** | Who provides the result: `tessera`, `std`, `glidesort`, `rayon`, `ips4o`. It is an identity and a display name only. | The catalog `implementations` table (renamed from `algorithms`) |
| **Route** | What an implementation calls for one operation and execution, whether it is stable, its family (radix, comparison, SIMD) and whether it is a semantic reference rather than a dedicated solver. | `Variant::prepare` and the runner's `list`; results record it |

Consequences:

- The catalog loses `modes`, thread-suffixed IDs and `tessera-full`; a full sort used as a selection reference is a route of `tessera`. Revision builds (`tessera-baseline`, `tessera-copy`) remain separate identities because they are different source trees, not routes.
- A displayed row name combines the implementation label and the route detail when they differ, such as "std · select_nth_unstable". Section titles derive from the operation and execution ("argsort", "par_argsort · 8 threads"), so no table maps entry points to labels.
- Stability is a property of the route; the existing rule that unstable record results never enter a stable ranking applies per route.

## Identities

Every case ID names every dimension, with no implicit default:

```text
operation/execution/type/distribution/length/seed[/parameters]
sort/serial/u64/random/65536/s1
argsort/t4/row_u64/random/1000000/s1
select_nth/serial/u64/random/65536/s1/32768
```

One formatter and decoder pair owns the grammar in TypeScript and in Rust, checked by the shared fixture; no consumer splits IDs itself. Criterion IDs become the case ID with the language prefix, without a trailing mode. A resumable group is `operation/execution/type/distribution[/parameters]`.

Existing IDs are not migrated. The tooling has no compatibility requirement before a release, and a translation table would be a second grammar to maintain. Tessera's Bencher history therefore restarts at the new IDs; the [main tracking](../development/continuous-benchmarks.md#main-long-term-tracking) data branch is rewritten in the same change. Retained local results keep their original tooling revision for regeneration, as retired workloads already do.

## Plans and CLI

- **Plan schema 3.** `schema` is a format version only. Every include rule may carry `operation` and `threads` alongside the input axes, and `exclude` rules may exclude any dimension. The `[[parallel]]` rule kind is removed. Live and retired operations are separate schemas: new selections accept only live operations, and the retained-result decoder alone accepts retired ones.
- **CLI.** `--operation` takes API names (`sort`, `argsort`, `select_nth`, `sort_by_cached_key`). `--threads` selects execution like `--lengths`. `--group` takes the group ID above. Direct executables take a plan instead of `--suite`. `compare algorithms` keeps its name; its help and the protocol define it as a comparison of implementations.
- **Cohorts.** `catalog.comparison` moves into each operation's entry, so each operation names its own ranking types and patterns.

## Results and publication

- **Run records** in `<implementation>/YYYY-MM.jsonl` add `operation`, `execution` and `routes` (route per case group, from the runner's listing). A tracking job measures one implementation, operation and execution, so each job keeps its own time budget, and the comparison takes the latest run per (implementation, operation, execution). An aggregate comes from one run; it never combines cases from different runs.
- **Index.** `<implementation>/index.json` gains `operation` and `execution` facets.
- **Growth.** `growth.json` is keyed by operation, because argsort's retained index output and in-place selection answer different memory questions.
- **Comparison.** `comparison.json` replaces its top-level `figures` with `operations: [{ id, label, reference, cohort, runs, figures }]`, ordered as the [figure guide](../development/benchmark-figures.md#fixed-visual-decisions) orders calls. `overview` remains the sort ranking.
- **Reports.** The denominator comes from the operation's reference route, and the figure guide line names it ("speed vs select_nth_unstable"). Non-sort operations use the existing row and curve templates; a new template needs a new question.

## Pages

`AlgorithmComparison` takes an `operation` and execution and renders that section of `comparison.json`. Each published operation has a ranking with memory, a pattern figure and a length figure, plus one figure per parameter axis (such as rank position for selection). The home page keeps the sort ranking. A summary of Tessera's speed per operation is deferred: each operation has its own denominator, and the figure would have to prevent reading ratios across denominators as comparable.

Per-operation references follow the [reference roles](../development/benchmarking.md#choosing-references-and-cases). The planned denominators are the standard library's direct precedent for each result:

| Operation | Denominator | Composition baseline |
|---|---|---|
| `sort` | `slice::sort` | — |
| `argsort` | Index vector sorted with `sort_by_key` | Tessera sort of (key, index) rows |
| `select_nth` | `select_nth_unstable` | Tessera full sort |
| `par_sort`, `par_argsort` | Rayon's stable sort of the same records or indices | Serial Tessera |

The strongest public implementations for selection and argsort are still to be surveyed; name them in this table only after their adapters verify.

## Stages

Each stage is a separate PR and changes no measured algorithm, input or sampling.

1. **Vocabulary.** Define the five concepts in [benchmark tooling](benchmark-tooling.md), rename `shape`, `suite`, `workload` and `mode` in code and documentation, and rename the catalog's `algorithms` to `implementations`.
2. **Catalog and IDs.** Add the `operations` table, the execution axis and the ID owner; remove `modes`, thread-suffixed IDs and `tessera-full`. Compare complete serial and parallel listings before and after, and check shard partitioning.
3. **Plan schema 3 and CLI options.** Rewrite the repository plans.
4. **Routes in results.** The runner lists routes, manifests retain them and reports take the denominator from the operation.
5. **Publication.** Rewrite tracking records, `comparison.json` and `growth.json`, reset the data branch and Tessera's Bencher history, and render per-operation sections. Then populate argsort and selection comparisons under the [CI scaling proposal](ci-scaling-proposal.md#keep-cross-algorithm-comparisons-out-of-pr-timing).

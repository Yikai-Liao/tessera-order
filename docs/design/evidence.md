# Engine evidence

This page keeps only what code and Git history cannot: how to read a small-case result, which experiments failed or stalled and must not be repeated blindly, which measured losses landed changes still carry, and how the engine's structure was judged. The full measurements of each accepted change belong in its PR description; commands, hashes and raw-result paths belong with the raw data outside Git. Entries describe their recorded revision and environment, not current-head validation. Use the [benchmark protocol](../development/benchmarking.md#run-an-experiment) for new measurements, and delete an entry when a change makes it obsolete.

## Reading small-case results

Process-level and three-block screens flag changes to investigate; only linked in-process comparisons with independent copies separate a source change from code placement, and even those do not bound all layouts. Identical instructions at another address moved short inputs by 20–90%:

| Investigation | Observation | Conclusion |
|---|---|---|
| Port vs prototype, ordered `u32`/`u128` | Ratios 0.53–1.28 in the measured build, 0.79–1.86 after a comment-only rebuild, 0.98–1.06 with `-x86-branches-within-32B-boundaries` | Skylake-SP keeps branches crossing 32-byte boundaries out of the µop cache (JCC erratum). Redirecting six identical probe functions to one address removed the `u32` gap |
| Low-fanout tiles (`e0ecd94` → `54926ca`), `random/48` | Identical copies differed by 21–22% against A/A of ±1.4–3.8%; moving the candidate's `sort_tile` body 160 bytes to the baseline address took 282–287 ns/sort back to 243–247 (baseline 237–243) | Tile code placement; the Intel runner's mechanism is unidentified |
| Serial CI artifacts (`fafaaa2` → `a26cac4`), `row_u64/equal/48` | Alert +6.9%; candidate/baseline 1.0231 against A/A 0.9672–1.0328; both executables ran the same 348 instructions | Placement sensitivity; a small whole-binary cost cannot be excluded |
| Eight-core parallel | Same-entry A/A 0.80–1.20 with inherited masks, 0.90–1.10 pinned, 0.78–1.22 on the pinned repeat | No stable detection window for a 5–10% source gain on this host |

Branch alignment is not a free speedup: it changed the prototype's own time by −30% to +69% across small cases. Stable Rust has no attribute for function or branch alignment, so a source change that helps one binary can hurt another. The crate has nothing to fix; benchmarks control placement ([source-attribution controls](../development/benchmarking.md#additional-source-attribution-controls)), and CLI builds default to 64-byte loop and block alignment.

## Port parity baseline

The engine is a Stable Rust port of the research prototype in `sort-research-rs` at `6c0877f0491dc3b8fc052aa529bce44bf8a53fa8`. Measured inside one Nightly binary of the prototype's harness (fixed seed, one pinned core, rotated order, every output checked), the median per-case ratio `port / prototype` was 0.984–1.004 over 27–136 cases per matrix (ranges 0.53–1.23, placement-dominated), for both `stable_sort_by_key` and `stable_sort`, in the default build and with `target-cpu=native` and fat LTO. Cases outside the control range were within 3% of the prototype forced onto cached bucket IDs (`record128` zipf 1.3 n = 128: 1.168 against 1.030), the cost of the caching policy the port adopts on purpose ([record handling](engine.md#record-handling)); its cost on 8-byte rows is an open [roadmap](../../ROADMAP.md#rust-01) question. The harness is Apache-2.0 code and stays outside the repository.

## Rejected or on hold

- **Flat samples as ordinary order candidates (R2), rejected.** Removing `Order::Flat` against `ef6c174` removed a state and a root-only branch, but constant inputs lost the vectorizable union/intersection scan: `u64/equal/65536` 0.839 / 0.834 and `row_u64/equal/65536` 0.925 / 0.921 (both baseline placements, A/A 0.994–1.006; `hot50`, `runs`, `two_values` neutral). Hosted [PR feedback](https://github.com/Yikai-Liao/tessera-sort/pull/105#issuecomment-6797484301), without placement controls, measured serial `u64/equal/65536` +70.0% and four-thread `u64/equal/1000000` +82.0%. Both hosted losses exceed the 10% limit, and [PR #105](https://github.com/Yikai-Liao/tessera-sort/pull/105) closed unmerged. A replacement must keep the constant-input scan; whether the loss is confined to all-equal inputs is unproven.
- **First-distinct-key order confirmation.** Removed more source but regressed 1,000-record constant inputs by 14–29%.
- **Ascending-first `confirm_order` reordering.** +6.6% instructions and 8–13% slower on `f64/sorted/65536`; reverted.
- **Streaming scalar scan for 99%-sorted budgeted insertion.** `u64/sorted99/65536` 1.2879 against A/A 0.989–1.011.
- **Removing the histogram maximum and testing insertion eligibility from bucket ends.** Matched the instruction saving but regressed `random/49` by 11–24% and `u64/random/1M` by about 14%.
- **Out-parameter for strict descent.** 2.4–5.3% slower on `u64/equal/65536` and `{u32,u32}/random/49`; strictness travels in the returned classification.
- **Early insertion finish for tiny inputs.** Regressed other small inputs.
- **Sample-weighted child work in tile planning.** Slower on `bimodal/1000` (1.316, then 1.057 with recursive projection) and `random/1000` (+2.7–3.5%) with +3–10% instructions; replaced by the bounded planner.
- **Parallel micro-tuning.** Index-only leaves and indexed final writes (14.8–18.4 ms against an 11.6 ms baseline), a frozen-directory wave (15.3 ms), cache-line-padded owners (inconclusive, A/A 0.909–1.091), source-aware free-block placement (relocation volume −15%, timing unverified) and a sorted free list. Final-scatter fusion **A** removed one 80 MB transfer per 80 MB input, and **B** also capped LSD digits at eight bits; ratios against the baseline were 0.982–1.102 (A) and 0.957–1.254 (B, slower on `u32`) against parallel A/A of 0.80–1.20. None entered the engine, and radix, final-scatter and relocation tuning is paused.
- **SIMD constraints** (AVX2, interleaved separate binaries, no paired protocol):
  - Dispatch belongs around the insertion pass. Per-scan dispatch cost more than it saved on random input, and a kernel outside its target-feature inlining context was 3.5× slower on sorted `u64` and 7× on sorted `f64`.
  - Materializing user keys on an 8,192-record near-sorted tile was 1.4–1.6× slower than scalar callbacks, so user-key tiles keep callbacks.
  - A sixteen-lane prefix sum lost to eight lanes (cross-lane swizzle).
  - Stable three-way compress scatter of 64K `u32` took 460 µs against 147 µs for scalar cursor writes, and AVX-512CD conflict detection would double the 32 KiB cursor table.

## Shared explicit direct-key scan

[PR #126](https://github.com/Yikai-Liao/tessera-sort/pull/126) consolidates integer, float and reversed-key traversal into one explicit `fearless_simd` scan. Native lane comparisons stay at the sealed key boundary; traversal, mask aggregation and tail handling have one owner. This bounded first S1 stage retains the peel, short-path policy and once-per-pass dispatch. Scalar-loop prototypes did not preserve the generated-code savings; the selected construction remains explicitly vectorized with LLVM loop and SLP vectorization disabled. Retiring the insertion extractor adapter is separate unfinished work, not a condition already satisfied by the shared loop.

Against the preceding merged head `81b5818`, normal and native linked-revision screens each cover `u32,u64,f64,reverse_u64,reverse_f64`, sorted/`sorted99`/`far_swaps`/random inputs, and 49/63/64/1,000/65,536 records, with two baseline placements, a current-source copy and repeated-current A/A. The normal screen uses nine blocks, the native screen three. Normal long-input integer/float scans remain within their controls; reversed long ordered inputs are favorable. These observations preserve the reason for the retired scans within the measured coverage, not a general source-causal speedup claim.

The stage individually accepts two short random costs. Normal-target `u32/random/49` has current/baseline 1.0544 / 1.0601, current-copy/current 1.0042 and A/A 0.9939–1.0061. Continuous `u64/random/49` reports 1.0651 with a 99% paired median interval of 1.0607–1.0739 on the documentation-follow-up head; the preceding implementation-head run reported 1.0024 for the same case. Both reports are retained, and the latter does not erase the former. The complete-loop consolidation is worth each roughly 6% local cost individually. Neither is offset by an aggregate gain or available as a budget for later changes.

## Root insertion ownership

R4 consolidates the complete root insertion attempt: the caller supplies effective tile capacity, while `insertion_probe` selects finishing or probing and owns the window and budget. It retains both low-level insertion entries (X4), the insertion-size predicate and every routing threshold; it reduces caller/callee coordination, not the number of insertion algorithms. Simply deleting the shortcut made `u64/random/48` about 49.5% slower in both linked baseline comparisons (baseline/current 0.6691 / 0.6692, A/A 0.9987–1.0013). Routing the unlimited leaf through the counted entry instead preserved the algorithm but changed generated-code work across the direct-extractor boundary. Keep the unit-return finishing entry inside the complete operation.

The three-block linked screen against post-ledger main still leaves short-input controls unresolved: `row_u64/random/48` baseline/current 0.9917 / 0.8918 and current-copy 0.9218 (A/A 0.9935–1.0065); `u64/random/48` 0.9776 / 0.9805 (A/A 0.9912–1.0088); `u64/random/65536` 0.9926 / 0.9897 and current-copy 0.9866 (A/A 0.9959–1.0041). Near-order short controls are wider and do not resolve their differences. Retained disassembly shows distinct root bodies and the preserved finishing branch, not code identity; no source-causal speedup or performance acceptance is established.

## Structure analysis

Compare constructions by their rules, states and invariants, not source length. A replacement must meet [semantics](../../conformance/semantics.md) and the [per-case acceptance rule](../../ROADMAP.md#simplification-candidates); showing each mechanism useful alone does not prove minimality. The maintainer-approved study ceiling is O(P^{3/2}√n), with fixed root fan-out R; an n-record buffer is excluded. The public [O(P√n) bound](../../conformance/semantics.md#rust-rayon-entry-points) changes only if an accepted design needs it.

**Ownership group.** `Partition` owns the adopted directory. The source ledger uses physical-owner locks, atomic source locations and registered free caches for both private staging and direct final bands. Recovery finishes bands before disarming the partition guard: staged/completed flags and `input_materialized` discharge different obligations. Gather transfers ownership; protected writes evacuate unread sources. The direct variant deletes parallel cycle permutation and compaction recovery rather than merely sharing their callbacks; serial materialization remains separate.

Differences inside the historical parallel A/A ranges are undetectable there. Compare copies, critical path, metadata and suspended buffers alongside timing. A and B may compose with C rather than compete with it; the rejected constructions below do not exclude their other forms.

### Post-ledger simplification proposal

[PR #120](https://github.com/Yikai-Liao/tessera-sort/pull/120) is merged: one source ledger already owns parallel recovery, with private staging and direct streaming as its two movement strategies. This proposal evaluates the remaining specializations against that implementation, not the pre-ledger engine. Source inspection supports the opportunities below; no new timing or code-generation experiment was run for this assessment. The brainstorm's isolated AVX2 compilation is a lead to reproduce in the actual dispatched path, not whole-engine evidence. Estimated source savings are not acceptance criteria, and there is no basis for claiming these candidates exhaust saving-preserving simplifications. [Roadmap](../../ROADMAP.md#simplification-candidates) owns their order, dependencies and completion criteria.

#### S1: One direct-key scan

The construction uses explicit `fearless_simd` vector operations, not automatic vectorization: one blocked scan owns traversal, pair-mask aggregation and tail handling; direct keys supply native lane counts and encoded-order pair comparisons. Integer and float comparisons share the loop, and `Reverse<K>` can reverse the underlying comparison by exchanging the pair sides rather than maintaining an automatically vectorized scan. This retires the separate integer, float and reversed scan loops without making LLVM's recognition of a scalar loop the mechanism that preserves their saving. Fixed-count scalar mask reductions produced packing, predecessor-shuffle and register-pressure costs in actual dispatched code; changing reduction spelling alone did not establish a saving-preserving replacement. These failures motivate an explicit vector boundary, not abandoning scan consolidation.

The adapter-retirement construction supplies a non-dispatching inversion operation to the insertion loop alongside `Direct`, instead of transporting the backend through `VectorKeys` or selecting a short-path `ByKey(|key| *key)` adapter. The scalar operation receives the same mutable extractor used for shifts, so callbacks and narrowed keys retain their own extraction. This retires the insertion-only unsafe extractor implementation and the scan method from the general extractor contract. Keep its acceptance separate from the preceding scan comparison. This changes a measured primitive, not just source organization: preserve the peel, short-input behavior and once-per-pass dispatch in the first comparison. Avoid dispatching again through `Direct` on each scan, and retain sealing. Validate the explicit vector path with LLVM loop and SLP vectorization disabled as well as in the normal build; scalar short, tail and unsupported-width fallbacks remain permitted.

Start with sorted and nearly sorted direct keys, where scan throughput matters, plus random and short-input controls. Inspect the real compiled path for integer and float widths, `Reverse`, pointer-sized and wide fallbacks on supported targets and the MSRV; an AVX2 loop alone does not establish baseline-ISA or non-x86 behavior. The shared comparison pipeline provides opt-in `Reverse<u64>` and `Reverse<f64>` inputs through the direct-key API ([protocol](../development/benchmarking.md#linked-revision-comparisons)); the first-stage [scan evaluation](#shared-explicit-direct-key-scan) records its scoped acceptance and placement limits. Adapter retirement and broader width/backend coverage remain open. Retain exact float bit ordering. Replacing the vector prefix sum is a separate measured change, and removing `fearless_simd` additionally needs a decision about runtime dispatch and explicit dependency approval; a scalar prefix sum alone does not make that dependency unnecessary.

#### P1: Stream with the same finishing capacity

The direct ledger removes the mandatory streaming temporary. Staging still gathers into a private bucket and writes it after sorting; streaming places prefixes directly into the final band before sorting. At equal child work, streaming removes one full-bucket transfer, excluding source evacuation. The current callbacks do not have equal child work: `sort_staged_child` enlarges the tile allowance up to the cursor limit, while `sort_child` uses the ordinary byte-bounded capacity. A final exclusive band can use the same allowance; private storage is not what makes tile counting safe. Whether that allowance explains the staging advantage remains unmeasured.

Compare (a) current staging, (b) streaming with ordinary capacity and (c) streaming with the staged allowance. Fix the root plan, shard count **and block size**: `block/parallel.rs` currently selects the block-size multiplier from bounded-finishing eligibility, so merely setting the staging limit to zero changes two mechanisms. Start with the historical large balanced case, then include record widths, skew and eligibility boundaries. Count source evacuation separately: gathering frees all a bucket's sources before its final writes, whereas streaming may evacuate more unread sources. Compare whole-call time and peak allocation, not only the omitted copy.

If (c) preserves the saving, one final-band callback can retire staged records/state, gather-sort-write completion, `BoundedFinish` and `bucket_limit`. The final design must give block sizing and effective tile capacity independent, general owners instead of retaining staging eligibility under another name. Removing private staging removes that particular suspended-bucket term, not all reentrant scratch or recovery obligations. Re-account retained tile/block scratch before revising the memory explanation. Applying enlarged capacity to serial subproblems is a separate routing experiment under the same capacity authority, not an automatic consequence of the parallel result.

#### N1/N3/N4: One split completion operation

Serial equality uses `partition_by`; parallel equality already encodes below/equal/above as a two-bit `ByKey` rank. A shared rank adapter and digit partition could retire the serial classifier entry and its optional callback path. Equality, existing runs and digit splits could then deliver bucket boundaries, remaining candidate bits and completed-band information to one child-finishing operation, with scheduling as a consumer. The boundary should own that complete operation rather than add a forwarding `Split` type around the existing loops.

The differences carry savings and progress rules. Equality's equal band is done but its outer bands retain candidate bits; digit and run splits consume bits, and the rotated run form must retain its no-partition route. Actual unchanged equality partitions still require a bit-consuming fallback: rank encoding does not solve N1 by itself, and a sample cannot certify progress. The adapter must cache user classification, decline payload filling and return the original extractor for child work. An earlier borrowed classifier measured 40% slower, so keep the closure owned. Preserve immediate serial tile finishing and avoid introducing an order scan where none runs today. A common loop earns its place only if these obligations have one owner without adding scans or per-record indirection.

#### N5: Shared node and tile recursion

Both executors plan and finish children, but they do not perform identical analysis. Serial compaction finishes tile-sized children without order confirmation; larger children confirm order; tile-local insertion-sized children skip variation scans, and all-small MSD buckets use whole-tile insertion. Root preparation has already supplied facts that child entry must not recompute. First share split completion, then test whether one recursive operation can preserve those facts and savings while tile counting retains its live-copy guard and scratch ownership. An unconditional `finish(records, candidate)` would discard information; a flag for every old entry point would merely rename the duplication. Small-input layout sensitivity makes this a structural experiment with unresolved timing risk, not an instruction-count-only acceptance.

#### T2: MSD-only tile finishing

One covering counting digit can finish without an LSD plan, but calling the current MSD path unchanged would add histogram-maximum work and may run insertion even when no candidate bits remain. Preserve terminal completion explicitly. Removing two-pass LSD is a different algorithm choice: it trades balanced cursor tables and alternating buffers for a larger top-digit table, copy-back, child scans and insertion or recursion. The proposed medium-density case is worth measuring alongside duplicates, sparse variation and wide records. Fewer planned passes or a simpler planner does not establish less total work; retain LSD if the general path cannot preserve its saving.

#### X1/X2: Reconstruct direct keys from counts

Sealed encodings are bitwise bijections. An inverse could replace each bucket's representative record with reconstruction from one full encoded base key and the bucket's digit, leaving parallel counting to reduce histograms. Preserve all bits outside the window, including the untouched half of a narrowed key, NaN payloads, signed zero and `Reverse`. User-key records remain ineligible because keys do not identify payloads. Removing representatives does not by itself unify serial/parallel scheduling or the extractor's two direct-key facts. Keep the serial path free of Rayon calls, and retain sealing when changing the trait surface.

This representation can be evaluated independently of S1; reduce scan-related extractor methods after S1 only if it succeeds. Keep the existing counting-window width in the structural stage. A wider histogram still has table initialization, reduction and O(P·2^width) storage costs, so widening needs a separate budgeted routing experiment, not just `decode`.

#### P4: Buffer ownership and child delivery

`Partition` holds a mutable `Buffers` borrow while taking and returning its directory allocations. Directly borrowing the relevant storage may remove that shuttle, but adoption and `Drop` must still see one complete owning directory and restore it before recycling. Evaluate this local change separately from replacing the `ends` pool. The latter participates in nested recursion and compaction: delivering a retired bucket does not release the parent partition's scratch. A receiver that queues serial children or dispatches parallel ones must preserve cache-hot tile finishing, bound queued metadata, and handle callback panic without revisiting a published borrow. Otherwise the new queue or borrow protocol replaces, rather than removes, complexity.

#### P5: Recursive parallel nodes

Large skewed children returning to the serial sorter motivate scheduling the same node operation recursively. The historical Zipf result identifies coverage to revisit, not proof that this is its only bottleneck. O(P√n) does not follow from each node meeting that bound: parent directories, suspended finishers, pooled allocations and an active frontier can coexist, while equality recursion has no key-width depth bound. A shared resource bound and a progress argument under reentrant callbacks must precede implementation. Do not solve the bound with worker permits that a suspended callback can hold while waiting for more work.

#### Structural acceptance needs calibration

The proposed distinction between structure and routing is useful for choosing evidence, but neither label makes instruction counts a latency guarantee. Counts can miss cache, vector-width, dependency-chain, dispatch and parallel-contention effects; the [counter tool](../development/benchmarking.md#fixed-work-counters) is serial and its simulated ISA can differ from the host. Work/copy models are especially useful where timing cannot resolve a difference, but equal counts do not establish that an alert is placement noise.

The earlier rejections were not all artifacts of a process-level limit: R2 lost the constant-input vector reduction, A changed packing and memory costs, and the first C prototype added a mandatory transfer. Their [recorded results](#rejected-or-on-hold) and construction-specific blockers remain valid; #120's individual exceptions do not generalize. A calibrated structural lane could prioritize fixed-work counts and movement/allocation models, with timing controls and explicit review of each unresolved loss. Until that policy is validated and approved, the existing per-case rule and [source-attribution controls](../development/benchmarking.md#additional-source-attribution-controls) remain in force. No candidate here authorizes a fast-path deletion or a performance waiver.

### Shared ledger study

The direct variant in [PR #120](https://github.com/Yikai-Liao/tessera-sort/pull/120) protects a complete destination prefix before resolving its relocatable source, eliminating the first prototype's mandatory streaming temporary and extra copy. The movement task finishes its final bucket after releasing all locks, without shared batch state or a second sorting dispatch; private staging keeps its previous eligibility and tile allowance. One flat table owns source length/location, and buckets retain ranges. This retires parallel permutation and compaction recovery within the public space bound, but not source protection or relocation. The maintainer explicitly accepts the measured skew trade-off: the final 97-case hosted screen at `f4d0783` reports four-thread `row_u64/skew99/1M` +9.8%; the local screen reports `row_u64` +18.6%, `row_u32` +11.2% and `u64` +10.0% on the same distribution/length. This is a scoped exception to the roadmap's local 10% limit, not a new performance budget. Causes remain unresolved; varying hosted short-serial alerts without a serial-source edit establish neither a layout cause nor a source-attributed gain. The accepted topology removes a recovery protocol while preserving staging and direct placement; above-window revision timing and placement-controlled skew attribution remain validation debt. Detailed measurements and checks stay in the PR.

The first C prototype kept bounded gather/sort/write eligibility and its tile allowance, but replaced fallback block permutation/compaction with one-prefix-at-a-time streaming through the same owner/location/free-cache ledger. Each streaming bucket allocates one block temporary before movement; its callback runs only after all its sources retire, every destination block has no unread source, and its temporary is released. Adjacent bands may then sort through disjoint fragments. At most R temporaries survive streaming, while staged suspension keeps the existing R·L bound, so the public O(P√n) bound remains. A movement kernel without allocation, scheduling or user code needs only whole-bucket completion state for recovery. Callback panics are caught per bucket and resumed after all jobs join; other callbacks may continue. An outer execution failure instead completes pending movement without callbacks before disarming the adopted directory guard. Concurrent publication adds a batch mutex, released before scheduling or key evaluation.

This genuinely deletes parallel cycle snapshots/completion and sequential compaction recovery, rather than wrapping two protocols. It retains physical-owner locks, atomic source locations, peer free discovery and protected final writes on roots that previously materialized without that ledger. [PR #118](https://github.com/Yikai-Liao/tessera-sort/pull/118) keeps the prototype in history and restores the accepted engine. Independent source/model and documentation review, complete serial/Rayon tests, Miri, ASan and platform/MSRV checks passed. Its paired screen still found four-thread losses of 22.6% on `row_u64/skew99/1M`, 13.4% on `u64/skew99/1M`, 11.9% on `row_u64/random/65536`, 11.1% on `row_u32/skew99/1M`, 9.6% on `u64/two_values/1M`, 7.2% on `row_u64/random/1M` and 6.9% on `u64/zipf2/1M`. None is accepted; these process-level alerts do not isolate source effects. Four above-limit losses reject the prototype as submitted despite its favorable aggregate. Bounded current-only large, above-window and skewed checks establish verified outputs/allocation, not revision gains. The result does not rule out a different source ledger or justify distribution-specific routing.

### Scattered completion study

Independent per-node arenas cost a frontier-dependent sum of square roots, with potentially linear growth before the fixed key domain saturates; fixed-width asymptotics alone do not reject them. A stronger B construction assigns at most P traversal lanes a shared arena, transfers child directory ownership depth-first, gathers tile leaves, appends completed leaves into a packed logical output stream sharing its final partial block, then materializes once after all lanes join. Lane reservations can survive callbacks if progress never waits for another permit. Accounting must include pending sources, suspended operations and completed output; equality recursion has no keywidth depth bound, so a digit-depth-only model would change equality routing.

This construction could retire staging’s owner locks, atomic locations and protected writes. We reject this specific gather–append–compact construction as a saving-preserving simplification: when eligible root buckets fit the same tile capacity, root scatter and leaf sorting match staging and no descendant packing is saved, but gather plus direct final writes becomes gather plus stream append plus final copying—three full-record transfers instead of two, excluding identical tile work and any relocation. It also defers a sequential full-output materialization until the lane join. Direct-final writes would need source/destination-overlap handling absent here; adopting tile output blocks or skipping already-final ranges would be different, untested constructions. The [counted model](../.vitepress/theme/sim/scatteredCompletion.test.ts) checks these transfers, join ordering and record conservation through tile errors, not arena reserves, Rust provenance or timing. Removed coordination could compensate in whole-call time; no measured slowdown or general impossibility is claimed. The historical staging comparison establishes why direct placement matters, not B’s penalty.

### Independent packing study

The independent A prototype first permutes blocks, then groups whole buckets into at most P output segments. Forward packing never overtakes an unread source; before packing, each segment snapshots the source suffix peers could overwrite beyond its final band. Accumulated partial-block slack is at most PR blocks per boundary, so snapshots across P segments cost O(P²Rb), or O(P^{3/2}√(Rn)) with balanced block length, plus block floors and directories. These buffers are bounded by segments even during callback suspension. Completed segments own exclusive final bands; recovery packs unfinished segments without callbacks before retiring the directory guard. This removes staging’s owner locks, atomic locations and free discovery but retains permutation recovery and adds snapshots and segment completion. One oversized bucket still dominates one packing segment.

[PR #117](https://github.com/Yikai-Liao/tessera-sort/pull/117) retained the prototype in history and restores the accepted engine. Ownership tests, independent review, Miri, ASan and platform/MSRV checks passed. Its paired revision screen nevertheless found parallel four-thread losses of 26.9% on wide-record sparse digits and 15.9% on `u64/far_swaps` (both 1M), plus 9.8% on `u128/sparse8`, 8.5% on wide-record random (both 1M) and a serial 7.9% on `row_u32/random/49`. These are process-level alerts, not established source effects; none is accepted. The two losses above the per-case limit and the larger memory ceiling reject this prototype as submitted, without claiming all independent packing is slower. Current-only large/above-window/skewed checks verify outputs and allocation, not revision gains.

Dependent packing could reduce boundary snapshots by waiting for consumed-source frontiers. That adds publication/wait rules; a finishing callback must not suspend before enabling a dependent source consumer, so release cannot simply coincide with local packing completion. This model restores ownership coordination and a release chain rather than preserving independent movement. It was not prototyped or timed; other constructions remain unexcluded.
